# 포트폴리오 문구

목표는 채용 담당자와 개발자가 **무엇을 구현했고 어디까지 확인했는지**를 바로 읽게 하는 것이다. 문장을 화려하게 만드는 작업이 아니다. 이전에 여덟 차례 문구를 검토해 승인받은 판단이 `docs/portfolio-wording-review*.md`와 `docs/copy-refinement-*.md`에 있다. 같은 위치를 다시 고치기 전에 관련 기록을 확인하고, 승인된 문구를 취향으로 되돌리지 않는다.

## 작업 방식 정하기

| 요청                                      | 동작                                                                                                                |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| "검토해줘", "어색한 곳 찾아줘", 전수 검토 | 대상을 고치지 않고 수정안 문서를 만든 뒤 승인을 받는다.                                                             |
| "고쳐줘", "다듬어줘", 구체적인 문장 지정  | 바로 반영하고 결과를 보고한다.                                                                                      |
| 새 소개, 새 항목 작성                     | 기존 데이터의 사실만 사용해 초안을 쓴다. 새 성과나 수치가 필요하면 `portfolio-project-refresh`로 근거부터 확인한다. |

## 문구 원칙

예시와 판단 근거는 [references/rules.md](references/rules.md)에 있다. 애매한 표현을 만나면 해당 절을 읽는다.

1. **구현한 동작과 대상을 앞세운다.** `안정적인 설계를 추구`, `등`, `관리`, `책임 경계`, `일부 연동`처럼 범위를 감추는 말은 실제 동작으로 바꾼다.
2. **자체 용어는 기능으로 풀어 쓴다.** 제품의 고유 메뉴명이 필요하면 괄호에 함께 적는다. 예: `인수인계 문서(바통북)`
3. **내부 영어 용어와 상태값을 그대로 노출하지 않는다.** `heartbeat` → `처리 기한 갱신`, `ACTIVE` → `미해결(ACTIVE)`
4. **정확한 실무 용어는 유지한다.** 트랜잭션, 멱등 키, 낙관적 잠금, Outbox, CSRF, Presigned URL, `SKIP LOCKED`, RPO·RTO, PKCE는 풀어 쓰지 않는다. `대사`처럼 낯선 용어는 처음 나올 때만 설명한다.
5. **한 문장에는 한 가지만 쓴다.** 구현, 검증과 제약이 한 문장에 섞여 있으면 나눈다.
6. **검증 수준을 넘겨 쓰지 않는다.** 구현, 로컬·자동화 검증, 공개 `main` 반영, 실제 배포·운영, 미검증을 구분한다. 측정값에는 조건을 붙인다(예: HLS 약 35초 → 약 17초는 팀 시연 환경). 측정하지 않은 효과(`장애가 줄었다`)는 쓰지 않는다. 릴리스 후보를 정식 배포로 쓰지 않는다. 테스트 데이터와 모의 응답은 그렇다고 표시한다.
7. **같은 대상은 한 이름으로 부른다.** 같은 결과물을 `보고서`와 `에디션`으로 섞어 쓰지 않는다.
8. **화면 위치에 의존하는 말을 쓰지 않는다.** 960px 이하에서는 배치가 바뀌므로 `왼쪽`, `오른쪽`, `아래` 같은 말은 틀릴 수 있다.
9. **영역마다 역할을 나눈다.** 개요에는 기능과 담당 업무, 문제 해결에는 선택한 방법, 검증에는 조건과 결과를 쓴다. 공통 안내(테스트 화면 여부, 브랜치 차이)는 한 번만 쓴다.
10. **제목은 짧게 쓰고 세부 조건은 본문에 둔다.** 추천 질문, 도식 제목과 카드 제목에 특히 적용한다.
11. **공개 대상을 밝힌다.** `공개`가 인터넷 전체를 뜻하는지 팀에만 공개한다는 뜻인지 구분한다.
12. **번역투를 줄인다.** `~를 통해`, `~에 대한`, `~하는 것이 가능`, `~를 진행`은 동사로 직접 쓴다. 결론을 먼저 쓰고 뜻을 더하지 않는 말은 지운다.
13. **AI가 쓴 글처럼 보이는 형식을 피한다.** 2026-10-06 사용자가 "AI 티가 난다"고 판단한 형식이다. 가운뎃점으로 명사를 나열하지 않는다(`주문·예약·스마트스토어 연동` → `주문, 예약, 스마트스토어 연동`, `결제·환불 키` → `결제와 환불 키`). 문장으로 끝낼 내용을 명사형으로 끊지 않는다(`… 확인. … 미검증` → `…을 확인했습니다. …은 아직 확인하지 않았습니다.`). 첫 문장은 정체성 선언보다 어떤 일을 해 왔는지 쓰고, 회사 이름은 경력에만 둔다. 화면을 설명하는 말(`제목을 누르면 펼칩니다`)은 쓰지 않는다. `100 RPS·300 TPS` 같은 고정 표기와 제품 이름은 예외다.

다음 내용은 바꾸지 않는다. 코드 식별자, 상태값, 명령어, 경로, 버전, 커밋, 테스트 수, 문서 원제, Hope 원작자 고지, 전자영장 성능 조건(100 RPS·300 TPS, 1시간)

## 같은 의미가 노출되는 위치

한 곳만 고치면 홈, 상세, 공유 이미지와 PDF의 설명이 서로 달라진다. 수정한 의미가 나오는 위치를 모두 확인한다. 같은 값은 데이터 파일에서 한 번만 정의하고 화면에 하드코딩하지 않는다.

| 노출 위치                       | 원본                                                                                                                                                               |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 홈 소개, 연표, 카드, 경력, 기술 | `src/data/homeHero.js`, `timeline.js`(연표 옆 결과), `profile.js`, `projectSummaries.js`(`homeSummary`·`homeStory`·`homeCheck`·`coverScreenshot`), `homeSkills.js` |
| 프로젝트 상세                   | `src/data/projects.js`, `caseHighlights.js`(소개와 확인한 범위), `batonServicePresentation.js`, `featuredProblems.js`, `warrantEvidence.js`                        |
| 도식                            | `src/component/project/diagrams/*.jsx`, 도식 제목 일부는 `ProjectCaseStudy.jsx`                                                                                    |
| 공유 이미지                     | `src/data/projectOg.js`. 본문 없이 이미지만 봐도 테스트 데이터나 개발 범위를 알 수 있게 쓴다.                                                                      |
| 검색 결과의 제목과 설명         | `src/data/routeMeta.js`                                                                                                                                            |
| 문서 검색 화면 안내, 추천 질문  | `src/component/search/PortfolioKnowledgePage.jsx`                                                                                                                  |
| 검색 자료                       | `src/data/knowledgeCorpus.js`의 추가 문구, `public/docs/**/*.md` 공개 요약 문서                                                                                    |
| PDF                             | 홈 데이터를 재사용한다. 인쇄 전용 문구는 `src/component/print/PortfolioPrintPage.jsx`                                                                              |
| README                          | `README.md`의 프로젝트 목록                                                                                                                                        |

`public/knowledge/portfolio.json`과 `docs/knowledge-document-snapshots.json`은 생성물이나 외부 저장소 사본이므로 직접 고치지 않는다. 홈 제목은 강조 구간 길이로 줄을 나누므로 제목과 강조 구간을 함께 고친다.

## 절차

1. **원문 수집.** 바꿀 표현을 `rg -n "<표현>" src public/docs README.md`로 찾는다. 전수 검토는 `portfolio-visual-check`의 `--all --expand --text --no-shot`으로 접힌 설명, 이미지 설명과 도식 문구까지 모은 `unique-lines.tsv`를 읽고, OG와 메타 원문은 데이터 파일에서 따로 확인한다.
2. **근거 확인.** 검증 범위, 수치 또는 공개 상태가 걸린 문장은 원본 저장소 문서나 커밋으로 확인한다. 확인하지 못했으면 문구 작업 안에서 범위를 넓히지 않고 보고한다.
3. **검토 문서(검토 요청일 때).** `docs/copy-refinement-YYYY-MM-DD.md`에 `번호 | 현재 문구 | 수정안 | 이유 및 위치` 표를 쓴다. 위치는 `[설명](src/data/projects.js:123)` 형식으로 링크한다. 우선순위는 사실과 다르게 읽히는 문구, 뜻이 모호한 문구, 길이와 반복 순서다. 승인 전에는 고치지 않는다.
4. **반영.** 위 표의 모든 노출 위치에 같은 의미로 반영한다. 반영 후 이전 표현이 남았는지 다시 검색한다.
5. **테스트 기대값.** `src/data/projects.test.jsx` 등은 특정 표현이 있는지(`toContain`), 없는지(`not.toContain`)를 확인한다. 같은 의미를 유지한 문구 변경이면 기대값을 함께 고친다. `not.toContain`으로 막은 표현(`기관 A`, `Apache Tika` 등)은 다시 쓰지 않는다. 단순 문구 수정을 위해 새 테스트를 만들지 않는다.
6. **확인.** `npm run check:file -- <변경 파일...>`로 형식과 대응 테스트를 확인한다. 변경한 화면은 1440px과 390px에서 줄바꿈과 넘침을 확인한다(`portfolio-visual-check`). OG, PDF, 검색 자료의 입력이 바뀌었으면 `portfolio-artifacts`로 갱신한다.
7. **기록.** 검토 문서가 있으면 끝에 `반영 및 검증 결과`를 추가한다. 실행한 검사와 확인하지 못한 범위는 `output/validation/last-run.md`에 남긴다.

## 보고

변경한 문장 수와 위치, 의미가 바뀌지 않았다는 근거, 함께 갱신한 산출물, 확인하지 못한 항목을 짧게 보고한다. 새 성과를 추가하지 않은 문구 작업이면 그 사실도 밝힌다.
