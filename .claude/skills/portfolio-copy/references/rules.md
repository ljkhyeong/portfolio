# 문구 판단 사례

`docs/portfolio-wording-review*.md`와 `docs/copy-refinement-*.md`에서 승인된 수정 사례다. 같은 유형의 표현을 만나면 판단 근거로 사용한다. 표의 문장을 그대로 다른 위치에 옮기지 않는다.

## 목차

1. 동작과 대상 드러내기
2. 자체 용어와 내부 용어 풀기
3. 검증 수준 지키기
4. 이름과 범위 맞추기
5. 문장과 제목 줄이기
6. 유지한 표현

## 1. 동작과 대상 드러내기

| 변경 전                                                         | 변경 후                                                             | 판단                                                            |
| --------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------- |
| 중복 실행 방지와 중단 후 재처리 등 안정적인 설계를 추구하는 …   | 중복 실행을 막고 중단된 작업을 재처리하는 …                         | `등`, `안정적인 설계`, `추구` 대신 구현한 동작을 쓴다.          |
| 요청 변환부터 제출 자료 반영까지 담당 범위를 분리해 처리합니다. | 기관별 요청 변환과 제출 자료 반영을 구현했습니다.                   | 무엇을 분리했는지 알 수 없다. 이 위치에는 담당 업무면 충분하다. |
| 주문별 재고 차이 반영                                           | 주문별 수량 변경분만 재고에 반영                                    | 무엇과 무엇의 차이인지 비교 대상을 쓴다.                        |
| 응답 및 후보 수신                                               | SDP 응답 및 ICE 후보 수신                                           | 종류를 밝혀야 기술 독자가 바로 이해한다.                        |
| Chromium 전체 미디어                                            | Chromium 카메라 및 마이크 제어와 화면 공유 테스트                   | `전체`처럼 넓은 말 대신 확인한 기능을 나열한다.                 |
| 메시지 보존과 별도 실패 큐 운영 지점이 늘어 …                   | RabbitMQ 메시지 보관 및 실패 큐 모니터링, 재처리 절차가 필요합니다. | `운영 지점` 대신 관리할 대상과 작업을 쓴다.                     |
| 독립된 코드 분석                                                | 이전 대화 없이 코드 분석                                            | 무엇에서 독립됐는지 밝힌다.                                     |

## 2. 자체 용어와 내부 용어 풀기

| 변경 전                        | 변경 후                                               | 판단                                                                     |
| ------------------------------ | ----------------------------------------------------- | ------------------------------------------------------------------------ |
| 조직 연속성                    | 담당자 공백 및 업무 지연                              | 추상적인 목적 대신 화면에서 확인하는 내용을 쓴다.                        |
| 바통북                         | 인수인계 문서(바통북)                                 | 용도를 먼저 쓰고 고유 명칭은 괄호에 함께 적는다.                         |
| 새 시도로 회수                 | 기존 시도를 종료하고 새 점검 실행                     | `회수`로는 동작이 드러나지 않는다. 도식에서는 `새 점검 실행`으로 줄인다. |
| ACTIVE 또는 RESOLVED 관심 항목 | 미해결(ACTIVE) 또는 해결됨(RESOLVED) 상태의 점검 항목 | 상태값과 사용자가 보는 뜻을 함께 쓴다.                                   |
| 짧은 RS256 참여권              | 만료 시간이 짧은 RS256 입장 토큰                      | `짧은`이 길이가 아니라 유효 기간이라는 점을 밝힌다.                      |
| heartbeat, payload, callback   | 처리 기한 갱신, 요청 본문, Core 콜백                  | 내부 영어 용어는 동작으로 바꾼다.                                        |
| `N → P`, `완료 → null`         | 처리대상(N) → 처리 중(P), 완료 후 처리 상태 초기화    | 기호만으로 쓴 상태 전이에 뜻을 붙인다.                                   |
| 미조회 시 재시도               | 요청 상태가 없으면 재조회                             | `미조회`는 조회하지 않음과 결과 없음이 섞인다. 조건을 쓴다.              |
| 전체 길이 커밋 ID              | 전체 커밋 해시                                        | 통상적인 Git 용어로 줄인다.                                              |

## 6. 유지한 표현

-   `같은 요청 8건에도 링크와 처리 기록 각각 1건`, `외부 API 대기 중 DB 연결 반환`, `서버 중단 후 미전송 알림 재처리`처럼 대상과 동작이 분명한 문장
-   프로젝트 문서로 확인한 수치, 커밋, 테스트 범위, 실제 운영과 미검증의 구분
-   전자영장 성능 테스트(100 RPS·300 TPS, 1시간), HLS 지연 개선(팀 시연 환경), LG CNS 컨소시엄과 기관 수, Hope 원작자 고지
-   화면에서 실제로 쓰지 않는 데이터 필드의 표현은 사용자에게 보이는 문제로 집계하지 않는다. 렌더링 경로를 먼저 확인한다.
