# 포트폴리오 화면

이 포트폴리오의 화면은 채용 담당자와 기술 면접관이 **경력과 구현 내용을 빠르게 찾아 읽게** 하기 위한 것이다. 일반 디자인 지침의 대담한 시각 실험, 큰 이미지 위주의 첫 화면, 장식 모션은 이 목적에 맞을 때만 적용한다. 2026-10-05까지는 도면형(가는 기준선, Fig. 번호, 치수선, 검증 단계 점)을 다듬었으나, 2026-10-06 사용자가 "AI 티가 난다"고 판단해 Claude Design 캔버스에서 새판 시안을 비교하고 **F4(연표 포스터) 메인과 P4(상세 확정안)**로 전면 개편했다(`docs/design-f4-2026-10-06.md`). 문구만 바꾸는 작업에는 디자인 절차를 적용하지 않는다(`portfolio-copy`).

## 판단 원칙

-   **읽는 순서를 먼저 정한다.** 이름과 직무 → 경력 → 대표 프로젝트(서비스 소개, 문제, 구현, 확인한 범위) → 기타 프로젝트 순서를 유지한다. 새 요소가 이 순서를 늦추면 다시 검토한다. 2026-10-06 개편 뒤에는 첫 화면 연표의 첫 줄이 경력이라 경력과 측정 결과가 첫 화면에 들어오고, 경력 카드 영역은 1440px에서 1,004px, 390px에서 1,450px에서 시작한다(메인 전체 1440px 4,532px, 390px 7,700px). 그림을 추가하면 `struct`의 outline 측정처럼 영역 시작 위치를 재서 전후를 비교한다.
-   **구조 장치는 정보를 담아야 한다.** 번호, 테두리, 상단 라벨은 실제 순서나 분류가 있을 때만 쓴다. 2026-10-06 개편에서 장식으로 읽히던 Fig. 번호, 모서리 십자 표시, 치수선, 번호 배지, 검증 단계의 상태 점과 칸 나누기를 모두 걷어냈다. 다시 넣지 않는다. 위계는 글자 크기, 제목 글꼴과 여백으로 만든다. 메인 첫 화면의 연표는 실제 기간을 그린 정보 그림이며, 막대 옆 글은 확인한 결과와 그 조건이다. 같은 카드 모양을 반복하는 구성, 모든 요소의 장식 그림자와 그라디언트는 피한다.
-   **확인한 범위는 문장으로 쓴다.** 상세 상단의 확인한 범위(`caseResults`)와 메인 카드의 확인한 범위(`homeCheck`)는 "어디까지 확인했고 무엇을 확인하지 않았는지"를 한두 문장으로 쓴다. 상태 점이나 확인됨·미검증 칸으로 바꾸지 않는다.
-   **실제 화면은 증거로 쓴다.** 개인 프로젝트 카드와 그 밖의 프로젝트에는 상세의 첫 화면(`coverScreenshot`)을 두고 촬영 조건(테스트 데이터, 모의 응답)을 함께 적는다. 상세의 대표 사례에 관련 화면이 있으면 `problems[].screenshotId`로 짝지어 사례 옆에만 두고 대표 화면 묶음에서는 뺀다.
-   **같은 정보를 두 번 보여 주지 않는다.** 2026-10-05 점검(`docs/design-frontend-audit-2026-10-05.md`, `docs/structure-trim-2026-10-05.md`)에서 겹치는 띠, 바로가기, 목록을 지웠다. 2026-10-06 개편에서는 측정 결과를 첫 화면 연표에만 두고 경력 카드에서 반복하지 않으며, 사례와 짝지은 화면은 대표 화면 묶음에서 뺀다. 새 요소를 넣기 전에 같은 화면의 위아래에 같은 내용이 있는지 본다. 긴 목록(대표 문서)은 앞의 6건만 펼치고 나머지는 `case-more`로 접고, 대표 사례 밖의 문제는 번호와 제목 색인으로 둔다.
-   **모바일에서는 줄이고 다시 배치한다.** 데스크톱 이미지를 그대로 축소하지 않는다. 메인 연표는 1100px 이하에서 항목마다 작은 기간 막대와 결과 한 줄을 단 목록으로 바뀌고(인쇄본도 같다), 경력과 개인 프로젝트 카드는 900px 이하에서 한 열로 쌓고, 700px 이하에서 기여 히트맵을 최근 21주로 줄인다. 800px 이하 메뉴는 두 줄이며 섹션 링크 줄은 옆으로 넘긴다. 상세 캡처는 700px 이하에서 옆으로 넘기는 띠로, 대표 사례의 네 칸은 한 열로 바꾼다.
-   **고정폭 글꼴은 영문 대문자 태그와 코드에만 쓴다.** 한글 라벨에 `--mono`나 넓은 자간을 주면 글자 사이가 벌어진다. `--mono`에는 한글 대체 글꼴로 Portfolio Sans가 들어 있지만, 공백은 여전히 고정폭이므로 한글 라벨은 `--sans`와 자간 0을 쓴다.
-   **이동할 수 없는 링크를 만들지 않는다.** 비공개 저장소처럼 방문자에게 404가 되는 주소는 `href` 없이 이름과 공개 범위만 표시한다(`CaseMetaSection`).
-   **모션은 사용자의 동작에 답할 때만 쓴다.** 접기와 펼치기, 확대 창처럼 변화를 보여 주는 경우에 쓰고 `prefers-reduced-motion`을 지원한다. 섹션마다 등장 애니메이션을 넣지 않는다.
-   **접근성 기준을 유지한다.** 키보드 초점 표시, 가로 스크롤 영역의 `tabIndex`와 `aria-label`, 이미지 대체 설명, WCAG AA 글자 대비를 지킨다.
-   **CSS를 지울 때는 계산값으로 확인한다.** 상세 화면 CSS는 `Project.css`·`BatonService.css` 같은 기본 규칙 위에 `CaseShowcase.css`가 덮이고, 운영 빌드에서는 청크 순서 때문에 개발 서버와 적용 순서가 다를 수 있다. 우선순위가 같은 두 규칙에 기대지 말고, 규칙을 지울 때는 여러 폭과 두 로딩 순서에서 요소 위치·크기와 계산값을 전후 비교한다.
-   **CSS 선택자 충돌을 확인한다.** 상세 화면은 `main.case-showcase …` 선택자로 공통 규칙을 덮어쓴다. 새 규칙을 추가하기 전에 같은 요소의 기존 규칙과 우선순위를 `rg`로 확인한다. `!important`로 해결하지 않는다.
-   **인쇄와 공유 이미지를 함께 본다.** 메인 컴포넌트와 데이터는 PDF에서도 쓰고, 일부 도식과 CSS는 공유 이미지에서도 쓴다. 공통 파일을 바꾸면 `portfolio-artifacts`로 산출물 입력이 바뀌었는지 확인한다.

## 큰 변경의 진행

레이아웃 재구성, 새 섹션, 메인 정보 순서 변경처럼 여러 화면에 영향을 주는 작업은 바로 구현하지 않는다. 먼저 현재 화면 캡처와 함께 짧은 보완안(바꿀 요소, 이유, 영향 화면, 모바일 배치)을 제시하고 승인받는다. 이전 사례처럼 비교 시안이 필요하면 `docs/design/`에 HTML로 남긴다. 작은 간격, 정렬, 넘침 수정은 바로 진행한다.

## 확인

1. 파일을 바꿀 때마다 `npm run check:file -- <파일...>`를 실행한다.
2. `portfolio-visual-check`로 변경한 화면을 확인한다. 공통 스타일이면 메인과 대표 상세, 영향을 받는 도식까지 확인한다. 캡처에서 줄바꿈, 정렬, 숨김 처리를 직접 본다.
3. 컴포넌트 동작을 바꿨으면 관련 테스트(`npm test -- <테스트 파일>`)와 오류 상태를 확인한다.
4. 인쇄 배치에 영향이 있으면 PDF를 다시 만들고 페이지 넘침을 확인한다. 화면과 인쇄 수정을 모두 마친 뒤 산출물을 생성하고 최종 빌드는 마지막에 한 번 실행한다.
