# BATON RELAY 응답을 잃은 이벤트의 중복 전달 차단

## 문제 상황

등록된 Discord·Slack·HTTP Webhook이 요청을 받거나 SQS FIFO 큐가 전송 요청을 수락했지만 RELAY가 응답을 받기 전에 종료되면 성공 여부를 모른 채 같은 이벤트를 다시 전달할 수 있습니다. SQS의 성공 응답은 큐 수락을 뜻하며 실제 소비자의 업무 처리 완료를 뜻하지 않습니다.

## 결정

-   대상 호출 전에 전송 시도 이력을 저장하고, 멱등 처리를 지원하는 대상에는 같은 중복 방지 키를 재사용합니다.
-   같은 이벤트 ID가 다시 들어오면 새 수신 이력과 등록된 전송 대상별 작업을 만들지 않고 기존 수신 결과를 반환합니다.
-   DB에서 다른 서버가 처리 중이지 않은 작업만 선택하고, 외부 요청 중에는 DB 연결을 반환합니다.
-   서버가 작업을 가져갈 때 처리 기한을 기록합니다. 기한이 지나 다른 서버가 이어받아도 같은 시도 UUID와 외부 서비스 멱등 키를 유지하고, 처리 서버만 변경합니다. 이전 서버의 늦은 결과는 저장하지 않습니다.
-   Discord·Slack·Webhook 또는 SQS 전송 요청의 성공 여부를 확인할 수 없으면 결과 미확인 상태(`OUTCOME_UNKNOWN`)로 멈춥니다.

## 적용 시 제약

중복 전달 방지를 우선하므로 결과 미확인 작업은 자동 재전송하지 않습니다. 운영자는 Webhook 수신 기록이나 SQS 전송 기록 등 외부 증거를 확인하고 성공 또는 실패 상태만 확정합니다. 상태 확정 과정에서 같은 이벤트를 다시 보내지 않습니다.

## 확인

같은 이벤트 재수신 때 등록된 전송 대상별 작업이 추가되지 않는지, 처리 서버 중단과 작업 처리 기한 만료 뒤에도 같은 시도 UUID와 중복 방지 키를 유지하는지 확인했습니다. 이전 서버의 늦은 응답 차단과 전송 결과의 운영자 수동 확정도 통합 테스트로 검증했습니다.
