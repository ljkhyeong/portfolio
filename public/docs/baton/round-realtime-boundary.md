# BATON ROUND 입장 토큰 검증과 WebRTC 연결 관리

## 책임

Core는 활동 중인 스터디 구성원에게 방 입장 토큰을 발급합니다. ROUND는 입장 토큰을 검증하고 최대 6명의 mesh WebRTC 연결 메시지를 전달합니다. 직접 연결이 어려우면 Cloudflare TURN 접속 정보를 발급합니다. 두 서비스는 DB를 공유하지 않으며 ROUND의 방과 참가자 상태는 프로세스 메모리에 저장합니다.

## 방 입장 권한 확인 방식

-   Core가 계정에 연결된 활동 중인 스터디 구성원인지 확인한 뒤 RSA 개인 키와 SHA-256을 사용하는 `RS256` 방식으로 서명한 짧은 입장 토큰을 발급합니다. 입장 토큰 쿠키는 방 경로로 범위를 제한하고, JavaScript에서 읽을 수 없으며 HTTPS 요청에만 전송되도록 `HttpOnly`, `Secure`, `SameSite=Strict`를 적용합니다.
-   ROUND는 Core의 공개 키 목록(`JWKS`)으로 서명, 발급자, 단일 수신자, 만료와 방 식별자를 로컬에서 검증합니다.
-   입장 토큰 갱신은 Core가 처리하고 WebSocket 및 TURN 요청만 ROUND로 전달합니다.
-   ROUND가 입장 토큰을 한 번 검증한 뒤에는 WebRTC 연결 설명과 네트워크 경로 후보를 전달할 때마다 Core를 다시 호출하지 않습니다. 따라서 Core 응답이 느리거나 일시적으로 실패해도 이미 입장한 참가자의 연결은 계속 처리할 수 있습니다.
-   같은 참가자가 새 입장 토큰으로 다시 입장하면 서버가 이전 WebSocket 세션을 종료하고 새 연결만 유지합니다.

## 연결 복구

-   연결마다 먼저 연결 설명을 만드는 브라우저를 하나로 고정해 동시에 offer를 만드는 충돌을 피합니다.
-   새 연결을 만들 때마다 순번을 올리고 연결 설명과 네트워크 경로 후보에 같은 순번을 넣습니다. 이전 연결 순번으로 늦게 도착한 메시지는 버립니다.
-   ICE 재시작으로 복구되지 않으면 피어 연결을 다시 만들되, 제한된 시그널링 재연결 동안 로컬 미디어는 유지합니다.
-   DataChannel 채팅은 메시지별 중복 제거와 애플리케이션 수신 응답을 적용합니다. 상대 브라우저 애플리케이션이 메시지를 받았다는 응답 수에 따라 전체 성공, 일부 성공과 실패를 구분하며, 사용자가 내용을 읽었다는 뜻은 아닙니다. 송신 대기 버퍼의 최대 크기도 제한합니다.

## 검증과 현재 범위

-   구현 기준: 비공개 `main` 커밋 `7c9218c`
-   통과: Chromium 전체 미디어, WebKit 호환성, Core 연동과 배포 검사 시나리오
-   보완 완료: WebKit 직접 연결용 mDNS와 배포 검증용 restic 누락
-   미검증: 실제 Cloudflare TURN 중계 전용 연결, Safari 실기기, 외부망과 6명 장시간 접속
-   운영 제약: 방과 참가자 상태를 메모리에 저장하므로 한 인스턴스로 실행
