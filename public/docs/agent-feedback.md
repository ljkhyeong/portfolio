# AI 코드 변경 검증 방식

## 적용 배경

토스 기술 블로그의 [AI가 팀 규칙을 지키도록 하는 방법](https://toss.tech/article/52631)을 참고했다.
글은 긴 작업에서 초기 지시를 놓치는 문제에 대응해, 파일 작성 직후와 작업 종료 전에 관련 규칙을 다시 전달하는 방식을 소개한다.
이를 개인 프로젝트의 언어와 계층 구조에 맞춰 파일 검사·전체 변경 검토·ArchUnit 검사로 적용했다.

## happyGallery에 적용한 흐름

1. 파일 수정 직후 파일 경로와 확장자로 검사를 선택한다. 프런트엔드는 ESLint, Java는 변경 모듈의 컴파일, 스크립트·JSON은 문법을 확인한다.
2. 작업 종료 전 시작 커밋부터 전체 diff를 만든다. 작업 중 커밋·스테이징·미커밋 변경·새 파일을 포함하고, 삭제된 파일도 확인한다.
3. Java·빌드 변경은 ArchUnit으로 웹의 저장소 직접 접근, 도메인의 외부 계층 의존과 서비스의 어댑터 구현체 참조를 검사한다. 같은 규칙을 CI의 Gradle 빌드에도 연결했다.
4. 검사 결과를 작업 중인 에이전트에 전달한다. 에이전트는 오류를 수정하고, 전체 diff에서 업무 책임·변경 누락·과한 추상화를 검토한다.

Codex 훅과 수동 명령은 `tools/agent-feedback.rb`를 함께 사용한다. 파일 검사는 `local <파일...>`, 종료 검사는 `final <작업 시작 SHA>`로 실행한다.
관련 Java 파일은 모듈별로 묶어 컴파일하고, 변경 없는 파일 검사와 문서 수정에 불필요한 빌드를 생략한다.
검사기에는 중간 커밋·새 파일 누락, 검사 실패 후 재시도와 중복 실행을 확인하는 회귀 테스트를 추가했다.

## 자동 검사와 AI 판단의 역할

파일 경로·확장자 패턴은 실행할 검사를 고른다. ArchUnit은 실제 클래스 의존 관계에서 선언한 규칙 위반을 찾는다.
검사 선택에 별도 LLM을 호출하지 않으며, 코드 수정과 설계 판단은 원래 작업 중인 에이전트가 수행한다.
자동 검사 통과가 업무 설계의 적절성이나 모든 기능의 정상 동작을 보장하지는 않는다. 전체 diff 검토와 변경한 기능의 테스트를 함께 수행한다.

## 확인한 구현과 참고 수치

-   happyGallery의 검사기·훅·회귀 테스트와 `LayerDependencyPolicyTest`, CI 연결 구성을 확인했다. 검사기 추가 커밋은 `f0476467`이다.
-   토스 글의 요청당 약 10초 추가 지연은 토스가 규칙 선택용 AI를 붙여 측정한 결과다. 내 프로젝트의 측정값이나 개선 성과가 아니다.
-   현재 구현은 검사 범위 선택에 LLM을 사용하지 않는다. 개발 시간 단축률이나 오류 감소율은 측정하지 않았다.
