# 전자영장 이중화 처리와 성능 테스트 반영

2026년 9월 8일 사용자가 제공한 구현 및 테스트 결과를 포트폴리오에 반영했다.

-   프로세스 내부 ReentrantLock에 의존하던 설명을 Oracle `FOR UPDATE SKIP LOCKED`와 DB 처리 상태에 따른 대상 선점으로 바꿨다.
-   `N(처리대상) → P(처리중) → null(처리완료)` 전환과 오래된 `P → N` 상태 복구를 설명했다. 재처리는 경과 시간과 주기별 점검을 따른다.
-   외부 API 호출과 전후 DB 처리의 트랜잭션 경계를 분리한 내용을 유지했다.
-   성능 테스트 조건은 **100 RPS·300 TPS, 1시간**이다. 커넥션 풀 고갈, 오류, DB 잠금 문제 없이 전량 처리했다는 제공 결과를 기록했다. 두 지표의 환산 관계나 최대 처리량은 추정하지 않았다.
-   사용자가 처음 보낸 1,500 RPS는 정정된 수치이므로 사용하지 않았다. 실제 성능 테스트를 이 저장소에서 다시 실행한 것은 아니다.

성능 수치는 `src/data/warrantEvidence.js`에서 관리하며 메인, 상세와 검색 자료에 같은 값을 사용한다. 메인 기술 사례와 대표 문제 해결 흐름을 갱신했고, 기존 기관별 변환·조회·PDF 응답 순서 역전 사례는 상세에 유지했다.

용어는 [Oracle SELECT 문서](https://docs.oracle.com/en/database/oracle/oracle-database/18/sqlrf/SELECT.html)의 `FOR UPDATE SKIP LOCKED`를 기준으로 정리했다. 테스트 로그와 환경 설정, 업무 소스는 추가로 공개하지 않았다.
