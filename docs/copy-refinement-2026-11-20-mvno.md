# 별정통신사 문제 해결 재검토

이 문서는 11월 19일 검토안의 우선순위를 대체한다. 이전 검토는 파일 이동과 조건부 갱신을 따로 평가하면서 실제 충돌 조건, 대상별 결과 처리와 설계의 제약을 놓쳤다.

요청한 저장소의 README, 소스 가이드, 결과 수집 인수인계, 변경 이력과 발송·번호 생성·재처리·상태 처리 코드, 관련 단위 및 통합 테스트 코드를 대조했다. 비공개 코드와 내부 규격은 옮기지 않았다. 테스트 코드를 읽은 것이며 직접 실행하거나 운영 성과를 측정한 것은 아니다.

## 대표 사례 선정

### 1. 재처리 시 추적번호 중복으로 거절되는 요청 처리

-   **문제:** 번호 자릿수가 제한된 통신사 규격에서 같은 날 재처리하거나 기존 번호 일부가 겹치면 추적번호(traceNum)가 중복돼 API 요청이 거절될 수 있다.
-   **판단:** 최초 발송은 순번을 올리고 재처리는 반대로 내려 번호 충돌을 줄인다. 그래도 중복 응답을 받으면 다음 순번으로 다시 요청한다. 일반 호출 실패를 무조건 재시도하는 방식과 구분한다.
-   **확인:** 중복 응답 후 다음 번호로 접수, 재처리 시 역방향 순번, 재시도 상한과 순번 소진을 다루는 테스트 코드를 확인했다. 접수된 번호가 결과 파일명에도 반영된다.
-   **한계:** 충돌이 발생하지 않는 전역 고유 번호 체계는 아니다. 제한된 번호 공간에서 충돌을 줄이고 명시적인 중복 거절에 대응한 설계다.
-   **권장 강조:** **최초 발송과 재처리의 순번 방향 분리**, **중복 거절에만 번호를 바꿔 재요청**.

### 2. 이중화 서버의 동시 파일 생성 충돌 처리

-   **문제:** 두 업무 서버가 같은 초에 파일을 생성하면 시간 기반 파일명이 겹칠 수 있다. 파일 존재 여부를 먼저 조회하는 것만으로는 두 서버의 동시 생성을 막을 수 없다.
-   **판단:** 공유 작업 폴더에서 CREATE_NEW로 파일명을 선점한다. 이미 사용 중이거나 송신 폴더에 남은 이름이면 다음 순번을 선택한다. 첨부 이미지와 XML을 함께 준비하고 이미지를 먼저, XML을 마지막에 송신 폴더로 옮긴다.
-   **확인:** 파일명 선점, 기존 파일 보존과 실패 시 임시 파일 정리 테스트를 확인했다. 서버 간 공유 폴더를 이용한 선점 및 송신 폴더 재확인 흐름은 구현 코드로 확인했다. 실제 NAS에서 두 서버를 동시에 실행한 검증으로 표현하지 않는다.
-   **한계:** EAI가 같은 초 안에 파일을 가져가면 이름 재사용 가능성이 남는다. 파일명 중복을 완전히 제거했다는 표현은 부정확하다.
-   **권장 강조:** **공유 폴더에서 파일명 선점**, **충돌 시 다음 순번 선택**.

### 3. 일부 대상의 실패가 확정된 결과를 덮지 않도록 분리

-   **문제:** 하나의 요청 파일에 여러 대상이 묶이지만 가입 여부와 처리 결과는 대상마다 다르다. 전체 요청에 결과 하나만 적용하면 뒤에서 발생한 오류가 앞서 확인한 비가입자 결과를 덮고 불필요한 재처리로 이어질 수 있다.
-   **판단:** 비가입자는 완료로 분류하고 발송 대상에서 제외한다. 이후 다른 대상의 조회나 파일 쓰기가 실패해도 확인된 비가입자 결과는 유지한다. 재처리에서도 완료 대상은 제외한다.
-   **확인:** 일부·전체 비가입자, 후속 조회 오류, 파일 쓰기 실패에서도 기존 결과를 보존하는 테스트와 대상별 상태 저장을 다루는 통합 테스트 코드를 확인했다.
-   **한계:** 비가입자 완료는 업무 처리가 끝났다는 의미이며 요청을 성공적으로 발송했다는 뜻이 아니다. 가입 여부를 확인하지 못한 오류는 비가입자로 처리하지 않는다.
-   **권장 강조:** **대상별 결과 보존**, **완료 대상 재처리 제외**.

## 상세 페이지 편집 방향

-   위 3개는 서로 다른 문제다. API 식별번호 충돌, 서버 간 파일명 경쟁, 요청 내 부분 결과 처리로 구분한다.
-   기존의 추상적인 ‘공통 처리와 기관별 변환 코드 분리’는 3번으로 교체하는 편이 낫다.
-   1번과 2번을 추가하되 각각 짧은 사례로 쓴다. ‘담당 구현’에는 기능 범위를 남겨 같은 설명을 반복하지 않는다.
-   실제 운영 장애 감소, 개선율, 중복의 완전 제거는 근거가 없으므로 쓰지 않는다. 별정통신사 연계는 개발 완료 후 통신사 테스트 중이며 2026년 11월 27일 오픈 예정이라는 상태를 유지한다.
